# Interview: handoff ledger direction

## Context

This interview followed a session-start assessment of the current
`projectkoios-bootstrap` handoff state.

The initial technical topic was JSON output for the existing handoff evaluator.
The discussion reframed that work away from a passive evaluator and toward a
portable, dependency-light protocol for provenance, process state, and future
message consumption.

The user explicitly stated that Codex should not implement code directly.
Codex's role for this slice is to clarify intent, document decisions, and
prepare routing/spec artifacts for the correct harness.

## User direction captured

- The desired near-term work is to build the evaluator/protocol capability, not
  to clean all handoffs first or stabilize Archon first.
- JSON output should not be merely a CLI report.
- Hermes is expected to evolve toward a deterministic orchestrator.
- Athena is conceptually `Codex + Archon`.
- Vulcan is `opencode`.
- Koios is `goose`.
- Athena, Vulcan, and Koios are expected to become message consumers.
- A pub/sub bus style architecture is likely, but should not be overbuilt now.
- The user sees current-state snapshots, event streams, and process headers as
  projections of the same JSON/message model.
- Each process should append to a message header.
- Provenance is a primary goal.
- The design should minimize dependencies so the core can be ported to other
  languages without porting a framework or dependency stack.
- "Evaluator" is not a good long-term word; it sounds too passive.

## Product versus meta-harness distinction

The user noted that, for the eventual Project Koios product, the natural
starting point may be Koios because the product is a knowledge management app,
with Prometheus acting as a content generator.

That is product architecture and belongs in `projectkoios`, not in this
bootstrap meta-harness repository.

For `projectkoios-bootstrap`, the relevant concern is the meta-harness process:
handoffs, provenance, routing, markings, guards, and deterministic coordination.

## Four courses of action considered

### Option 1: Header-only ledger projection

Treat each existing handoff file as one ledger message. Parse current headers
and body, emit JSON with a generated `message_id`, but do not invent transition
history yet.

Pros:
- Smallest step toward provenance.
- Easy for Vulcan to implement.
- Low migration risk.
- Current markdown handoffs remain valid.

Cons:
- Provenance is shallow.
- Does not yet model the SDLC as transitions.
- Harder to distinguish artifact state from process history.

Best if the goal is a quick JSON baseline before changing the process model.

### Option 2: Inferred transition ledger

Treat each handoff as a message with an inferred transition history. Every
current artifact gets at least one transition, usually `created`, derived from
headers. Later transitions can include `routed`, `reviewed`, `validated`,
`completed`, `superseded`, and `rejected`.

Pros:
- Establishes provenance as history, not static metadata.
- Still read-only and dependency-light.
- Fits Petri-net thinking: transitions produce markings.
- Gives future bus consumers a stable shape.

Cons:
- Some transition data will be inferred, not directly recorded.
- Requires careful naming so inferred history is not mistaken for audited
  history.
- More implementation than a header-only JSON report.

Best if provenance semantics should start now without building a full ledger
writer.

### Option 3: Explicit append-only ledger format

Define a new canonical ledger section or sidecar JSON format where every
process action appends an immutable event. Current handoffs become legacy inputs
that can be imported into the ledger.

Pros:
- Strongest provenance model.
- Clean separation between artifact body and process history.
- Best long-term fit for deterministic Hermes and pub/sub consumers.
- Avoids pretending old headers contain full provenance.

Cons:
- Bigger migration.
- Requires deciding storage format now.
- More process overhead before current handoffs are cleaned.
- Higher chance of designing too much too early.

Best if provenance correctness matters more than incremental compatibility.

### Option 4: Bus-envelope ledger contract

Design the ledger as the future pub/sub message contract immediately. Every
record is a bus-compatible envelope with fields such as `topic`, `message_id`,
`causation_id`, `correlation_id`, `place`, `transition`, `producer`,
`consumer`, and payload.

Pros:
- Directly aligns with deterministic Hermes plus Athena/Vulcan/Koios consumers.
- Strong event architecture foundation.
- Easier future transport swap because JSON envelope is already canonical.

Cons:
- Highest design burden.
- Risks importing distributed-systems complexity too early.
- May overfit before the process model is proven locally.
- More concepts to port across languages.

Best if the bus architecture is the main artifact to stabilize now.

## Decision

The user selected Option 2: inferred transition ledger.

## Interpretation

The next work should not be framed as "add JSON output to the evaluator."

It should be framed as:

```text
Build a read-only handoff ledger projection.
```

The first slice should implement this pipeline:

```text
handoff files
-> message records
-> inferred transition history
-> current marking
-> guard violations
-> deterministic JSON projection
```

## First-slice constraints

- No file mutation.
- No pub/sub transport.
- No full ledger writer yet.
- No external dependencies.
- Existing markdown handoffs remain the source input.
- Each handoff emits one message with at least one inferred `created`
  transition.
- Every inferred transition must be labeled as inferred, not audited.
- The model should remain portable to other languages.

## Suggested vocabulary

Avoid using "evaluator" as the long-term conceptual name.

Candidate vocabulary:
- handoff ledger
- ledger projection
- protocol core
- handoff protocol core
- process marking
- guard violations
- inferred transitions

The current evaluator can be treated as the first read-only implementation
slice of the handoff ledger/protocol core.

## Implications for Vulcan handoff

A downstream Vulcan implementation handoff should request:

- a read-only handoff ledger projection command or mode
- deterministic JSON output
- message records derived from existing markdown handoffs
- one inferred `created` transition per message
- markings computed from those messages
- guard violations emitted against message identifiers
- no mutation of handoff files
- no event bus implementation
- no new external dependency
- tests covering the JSON shape and inferred-transition labeling
- fixes for known role-normalization false positives, including labels such as
  `Vulcan (opencode)` and `Hermes (pi)`
