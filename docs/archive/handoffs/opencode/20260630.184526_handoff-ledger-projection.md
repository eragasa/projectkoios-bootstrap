# Implementation brief: handoff-ledger projection

## Objective

Implement a read-only handoff-ledger projection CLI command. The design questions from the architecture spec have been resolved in `adr.20260630.170000_pending-athena-decisions.md` (Accepted). The spec is self-contained; no further design invention is needed.

## Source artifacts

- Architecture spec: `docs/archive/handoffs/archon/20260630.141739_handoff-ledger-projection-spec.md`
- Decision record: `docs/architecture/adr/adr.20260630.170000_pending-athena-decisions.md`

## Resolved design decisions

These were the open questions in the spec. All are now final:

| Question | Decision |
|----------|----------|
| **message_id scheme** | Path-derived — repo-relative path from `docs/archive/handoffs/` |
| **generated_at** | Omitted by default; `--with-timestamp` flag |
| **Command shape** | New `handoff ledger` command |
| **Unparseable files** | Included in `skipped` array with reason |
| **Status field** | Message payload only for first slice |

## Implementation tasks

1. Extend or wrap the existing `HandoffParser` / `HandoffEvaluator` flow into a read-only ledger projection model.
2. Add dataclasses or typed structures for messages, transitions, and projection output.
3. Keep conversion from `HandoffArtifact` to message/projection records pure and deterministic.
4. Emit JSON through the existing CLI via `projectkoios handoff ledger --json`.
5. Add `projectkoios handoff ledger --json --with-timestamp` variant.
6. Include `skipped` array for unparseable handoff files with a reason string.
7. Use path-derived `message_id` = repo-relative path under `docs/archive/handoffs/`.
8. Update guard violation output so JSON consumers can resolve violations back to message records.
9. Add focused pytest coverage for the acceptance criteria.
10. Write a Vulcan implementation report in `opencode/handoffs/`.

## Acceptance criteria

From `docs/archive/handoffs/archon/20260630.141739_handoff-ledger-projection-spec.md`:

1. A read-only ledger projection is available from the existing `projectkoios` bootstrap CLI.
2. Running the projection over the current repo mutates no files.
3. Existing markdown handoffs remain the only source input for the first slice.
4. Each parsed handoff produces exactly one message record.
5. Message identifiers are deterministic across repeated runs over unchanged files.
6. Each message has at least one `created` transition.
7. Every first-slice transition is explicitly labeled with `source: inferred`.
8. Transition evidence distinguishes inferred history from audited history.
9. The projection includes a current marking keyed by place name and containing message identifiers.
10. Guard violations reference message identifiers and source paths rather than only raw filesystem paths.
11. JSON output is deterministic apart from any intentionally documented generation timestamp (`--with-timestamp`).
12. The implementation adds no new external runtime dependency.
13. Tests cover message ID stability, inferred-transition labeling, marking projection, guard violation projection, and no-mutation behavior.
14. Tests cover role/provenance normalization cases such as `Vulcan (opencode)`, `Hermes`, `Athena (archon)`, `Codex`, and `Delegated-Operator: Codex`.
15. Existing `handoff evaluate` behavior remains compatible unless Athena explicitly authorizes a breaking CLI change.

## Out of scope

- A message bus, topic subscriptions, or background daemons
- Cross-repo transport
- Mutation of handoff headers
- An append-only sidecar event store
- Conversion of markdown handoffs into a new canonical format
- Long-term product architecture for the `projectkoios` mothership repo
- Status-field transition inference (deferred to later slice)
