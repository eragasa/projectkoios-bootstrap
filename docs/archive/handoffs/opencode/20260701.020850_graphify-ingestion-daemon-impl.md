# Implementation brief: Hermes Graphify ingestion daemon (first slice)

## Objective

Implement the smallest Graphify daemon bootstrap slice per the Accepted ADR
`docs/architecture/adr/adr.20260701.004713_graphify-ingestion-daemon-bootstrap.md`.

The daemon is a Hermes-owned local background service that performs an initial
full Graphify build over this repository, then watches the repository
filesystem for eligible changes, debounces and coalesces them, runs the smallest
practical refresh, and publishes updated local Graphify snapshots, universal
chunk cards, run metadata, freshness markers, and degraded-state reports to
Hermes-local runtime state. The daemon is scoped to `projectkoios-bootstrap`
only. It is not a general ingestion engine.

No code is implemented from this brief until Vulcan accepts it. Vulcan owns
implementation; Hermes owns routing and validation.

## Hermes-resolved implementation choices

Vulcan must follow these implementation choices. They are not in the ADR; they
are Hermes routing decisions that narrow implementation freedom.

### 1. CLI verb

Add a new top-level CLI parser branch `projectkoios ingestion daemon` alongside
the existing `bootstrap` and `harnesses` branches in
`src/python/projectkoios/bootstrap/cli.py`.

The word `ingestion` appears **only** as a CLI verb. There is no
`projectkoios.ingestion` Python package. This honors ADR non-goal:
"Do not build or name `projectkoios.ingestion`."

### 2. Module path

Daemon implementation lives under the existing CPN-bearing namespace:

```
src/python/projectkoios/bootstrap/harness/daemon/
```

Co-located with the existing CPN types in `bootstrap/harness/data/`
(`ArtifactToken`, `Marking`, `Violation`) and `bootstrap/harness/handoffs/`
(`evaluator`, `guards`, `parser`, `topics`). This is YAGNI-compliant: no new
top-level namespace and no speculative surface.

The daemon module **must not** be named `projectkoios.ingestion`.

### 3. Ollama client

Use stdlib `urllib` to call local Ollama at `localhost:11434`. No new pip
dependencies. If Ollama is absent or unreachable, the daemon must degrade
gracefully: emit a warning in run metadata, skip universal chunk-card
generation for the affected run, and keep the graph snapshot fresh. This
matches the ADR's degraded-snapshot behavior.

### 4. Filesystem watcher

Use stdlib `asyncio` polling on `os.scandir` / `os.stat` mtimes with
debounce and coalesce. No `watchdog` dependency. One follow-up update is
scheduled when changes arrive during an active update (per ADR). Polling
interval is an implementation detail for Vulcan; pick a sensible default.

## Colored Petri net modeling requirement

This is a hard requirement, not a suggestion. The daemon's internal state must
be modeled as Colored Petri net DataObjects and ActivityObjects, consistent
with `adr.20260630.042202_colored-petri-net-meta-harness` and the existing
implementation in `bootstrap/harness/data/` and `bootstrap/harness/handoffs/`.

### Reuse existing CPN types

Reuse the existing token, marking, and violation types from
`bootstrap/harness/data/` where they fit. Do **not** duplicate
token/marking/violation vocabulary in a parallel namespace. New token kinds
are fine; new parallel type hierarchies duplicating `ArtifactToken`,
`Marking`, or `Violation` are not.

Reference implementations to study before writing new types:

- `src/python/projectkoios/bootstrap/harness/data/artifact.py` — `HandoffArtifact` (colored token shape)
- `src/python/projectkoios/bootstrap/harness/data/marking.py` — `Marking` (token distribution across places)
- `src/python/projectkoios/bootstrap/harness/data/violation.py` — `Violation`, `ViolationCode`
- `src/python/projectkoios/bootstrap/harness/handoffs/guards.py` — guard functions with `enabled()`/`apply()` shape
- `src/python/projectkoios/bootstrap/harness/handoffs/topics.py` — `Message`, `Transition`, `Topics`, `TopicsView`, `build_topics_view` (read-only projection pattern)

### DataObjects (state)

Model daemon runtime state as DataObjects. Suggested minimum:

- `daemon_run` token kind — one per daemon invocation or update cycle
- `graph_snapshot` DataObject — reference to the current published graph
- `chunk_card_set` DataObject — reference to the current published chunk cards
- `freshness_state` place set: `fresh`, `updating`, `degraded`, `stale`, `failed` (the five states named in the ADR)
- `run_metadata` DataObject — the recorded metadata block described in the ADR `architecture-spec`

These are first-slice DataObjects only. Do not speculatively model
vault/PDF/workspace/directive/overlay states — those are ADR non-goals.

### ActivityObjects (transitions)

Model daemon actions as ActivityObjects (transitions) with an `enabled()` and
`apply()` shape, mirroring the guard/transition pattern in
`bootstrap/harness/handoffs/guards.py`. Suggested first-slice transitions:

- `InitialFullBuild` — performs the first full Graphify build over the repo
- `WatchFilesystem` — long-running watcher observing the source root
- `ScheduleUpdate` — debounce and coalesce layer; turns event bursts into one update request and schedules one follow-up when an update is in flight
- `RunGraphifyRefresh` — incremental or refresh Graphify run using defaults
- `GenerateChunkCards` — local Ollama universal chunk-card generation
- `PublishSnapshot` — write fresh snapshot, chunk cards, metadata, freshness marker
- `PublishDegradedSnapshot` — write partial snapshot with warnings and failure metadata

Each transition consumes and produces DataObjects and updates the freshness
marking. The marking must be expressible so a future read-only projection
(like `handoff topics`) can observe daemon state through the same CPN
vocabulary.

### YAGNI constraint

Implement only the ADR's first-slice transitions and DataObjects. Do not
speculatively model states or transitions for vault, PDF, whole-workspace,
directive queue, role-specific overlay, custom entity/relation ontology, or
per-agent bootstrap work. Those are ADR non-goals. If a transition or
DataObject is not required by the ADR's acceptance criteria, do not add it.

## Acceptance criteria

Copied verbatim from the ADR `acceptance-criteria`. Vulcan must satisfy all of
these:

1. The daemon is scoped to `projectkoios-bootstrap` only.
2. The daemon is Hermes-owned local runtime, not Archon, Koios, or Vulcan-owned runtime.
3. The first supported mode is a real local background watcher with an initial full Graphify build.
4. Filesystem events trigger updates through debounce and coalesce behavior.
5. If events arrive while an update is running, the daemon schedules one follow-up update rather than running overlapping refreshes.
6. Source inclusion follows Graphify-supported files under the repo root after `.gitignore`-style, generated, runtime, sensitive, and daemon-output exclusions.
7. Graphify default chunking is used unless a later accepted ADR changes it.
8. Effective chunking parameters and Graphify/Ollama tool versions are recorded in run metadata.
9. Local Ollama produces universal chunk cards for all agents.
10. Universal chunk cards are not role-specific overlays, review-only hints, or a durable knowledge ontology.
11. Generated graph data, chunk cards, run metadata, and degraded-state reports live under Hermes-local runtime state such as `~/.pi/koios-ingestion/projectkoios-bootstrap/`.
12. Generated runtime output is not committed to this repository.
13. Partial processing failures publish a degraded or stale snapshot only with visible warnings and file-level failure metadata.
14. The daemon detects unexpected source-tree changes caused by its own run and fails or warns rather than silently corrupting the working tree.
15. Agents can discover output through the documented default path convention.
16. No code is implemented from this Draft ADR until Hermes routes an accepted ADR to Vulcan. (Satisfied by this routing.)

## Validation expectations

Copied verbatim from the ADR `validation-expectations`. Hermes will require
Vulcan to provide a safety-focused functional validation report before marking
implementation complete.

Validation must show:

- the daemon can perform an initial full build for `projectkoios-bootstrap`
- the watcher reacts to eligible filesystem changes
- excluded paths do not trigger ingestion
- generated/runtime/sensitive paths are excluded
- daemon output is written under Hermes-local runtime state, not the repo
- `git status --short` does not show daemon-generated output or source-tree mutations after a daemon run, except intentional implementation files
- event bursts are debounced into one update
- changes arriving during an update schedule one follow-up update
- partial file failures produce degraded or stale warnings
- run metadata records Graphify version, effective chunking parameters, Ollama model metadata, trigger kind, processed files, skipped files, failed files, and freshness state
- universal chunk cards are produced for at least one changed or indexed chunk
- agents can locate output by the documented default path convention

Validation may use temporary files inside the repository for the test, but the
daemon must clean up its generated runtime output outside the repo and must not
capture secrets or machine-local state in committed files.
