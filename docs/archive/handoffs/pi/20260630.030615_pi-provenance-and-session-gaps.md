# pi harness: provenance validation and session protocol gaps

## Discovery context

This report follows the routing-chain deviation documented in
`archon/handoffs/20260630.030355_routing-chain-deviation.md`.
While investigating that defect, several pi-side gaps were identified
that made the violation possible.

## Gaps

### 1. No inbound provenance validation

pi does not currently check whether a handoff it receives was written
by a legitimate pi session. The handoff in
`pi/handoffs/20260630.024714_projectkoios-current-state-routing.md`
was written by Codex, not by pi, and `pi/AGENTS.md` has no rule or
checklist item that would catch this.

Recommendation: define a provenance check at session start —
validate that inbound handoffs claiming pi origin were produced by a
session running under pi instructions.

### 2. Session protocol is underdefined

The root `AGENTS.md` defines a start/stop session protocol for pi,
but `pi/AGENTS.md` does not reference or reinforce it. By contrast,
`opencode/AGENTS.md` has its own self-contained session checklist
and `rules/session.md`. This makes pi's session behavior implicit
and harder to enforce.

Recommendation: add a session protocol section to `pi/AGENTS.md`
(like opencode has) that includes handoff provenance checks as a
start-of-session step.

### 3. Contradictory Codex-as-pi language

Root `AGENTS.md` says Codex "may perform these operator actions on
behalf of the workflow" but "should not describe itself as pi." This
is contradictory — it authorizes pi-level action without requiring
the role label that carries accountability.

Recommendation: resolve the contradiction one way or the other.
Either Codex can act as pi (with appropriate provenance headers on
its handoffs) or it cannot (with a clear "Codex must not write
routing decisions or implementation handoffs" rule).

### 4. No rejection mechanism for invalid handoffs

When pi encounters a corrupted chain, there is no defined mechanism
to reject the offending artifact and signal back to the sender.
Compare with opencode, which has `deviation-report` as a standard
artifact type.

Recommendation: add a `routing-rejection` or `provenance-flag`
artifact type to pi's toolset, or explicitly borrow the
`deviation-report` convention.

## Status

This report is a finding, not a request for immediate implementation.
It documents pi-side vulnerabilities that allowed the Codex-as-pi
bypass to pass undetected.
