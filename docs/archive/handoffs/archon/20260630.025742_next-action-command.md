# Architecture task: next-action recommendation command

## Objective

Specify a `projectkoios bootstrap next-action` command that reads active
handoffs and recommends the next operator route.

## Context

During the current session, Codex repeatedly decided the next step from artifact
state:

- Codex-to-Codex routing handoff led to an Archon run.
- Archon clarification led to a Vulcan handoff.
- Completed artifacts were committed before downstream work continued.

Those decisions should become a small read-only recommendation command.

## Candidate behavior

The command should inspect active handoffs and produce recommendations such as:

- active `pi -> Codex`: continue operator intake or run Archon if specified
- active `archon -> pi`: review spec and create an implementation handoff
- active `pi -> Vulcan`: run or notify opencode/Vulcan
- completed implementation report: run completion gate
- validated result with durable knowledge need: route to Goose

## Architecture questions

- Should recommendation rules be hard-coded, documented, or data-driven?
- How should conflicting active handoffs be reported?
- Should the command understand artifact types from headings/body text or only
  headers and paths?
- Should it ever return a nonzero exit code?
- How should it handle stale active artifacts?

## Expected Archon output

- architecture-spec
- acceptance-criteria
- implementation-brief
- routing rule table
- non-goals

## Initial acceptance criteria

- The command is read-only.
- The command reads active handoffs from known handoff directories.
- The command prints one primary recommendation and any blocking conflicts.
- The command explains which artifact caused the recommendation.
- The command handles no-active-handoff state gracefully.

## Non-goals

- Do not execute the recommended action.
- Do not mutate handoff status.
- Do not run Archon, opencode, or Goose.
- Do not replace human/operator judgment.
