## Design questions for Athena

1. **Role scope**
   - Is Koios only a knowledge harness, or also a first-class repo analysis and documentation operator?

2. **Artifact model**
   - Should Koios own additional typed artifacts such as:
     - repo-state-summary
     - provenance-audit
     - knowledge-sync-note
     - documentation-gap-report
     - routing-recommendation

3. **Routing rules**
   - What requests should route directly to Koios instead of Hermes, Athena, or Vulcan?
   - What requests should Koios handle only in a support capacity?

4. **Operational boundaries**
   - What level of direct editing is in scope for Koios?
   - Should Koios be limited to docs/knowledge/provenance work, or may it perform small code/config fixes when low-risk?

5. **Capability contract**
   - What minimum tools/capabilities should the Koios harness require?
   - Which are mandatory vs optional:
     - file editing
     - shell access
     - code analysis
     - graph/query tooling
     - vault integration

6. **Skill / prompt infrastructure**
   - Should Koios have a dedicated skill or operating manual similar to Hermes session-start and handoff procedures?
   - Should there be a canonical goose/Koios prompt or workflow definition in this repo?

7. **Knowledge provenance**
   - What provenance standard should Koios enforce when converting session outcomes into durable knowledge?

- the primary harness for **knowledge capture, provenance, repo understanding, and documentation coherence**
- a secondary harness for **lightweight repo support work** when specialist routing would add unnecessary ceremony
- a consumer and producer of typed artifacts that preserve durable knowledge across sessions and repositories
