# Harness role clarification plan

## Scope

Plan a docs-only clarification update for `projectkoios-bootstrap` so harness roles, routing, and provenance are stated consistently in `AGENTS.md`, `pi/AGENTS.md`, and closely related bootstrap/harness docs.

This artifact is planning/specification only.
It does **not** authorize direct edits in this artifact itself, and it does **not** treat Codex as `Hermes`.

## Problem statement

Current wording leaves ambiguity about:
- whether Codex is acting as `Hermes` or merely invoking Archon on behalf of an operator
- whether `Hermes` is a single global harness or a router that can dispatch work into individual Project Koios repositories
- how local repo-specific meta-harness state relates to shared bootstrap guidance in `projectkoios-bootstrap`
- how provenance should distinguish the original request source, the sender, the acting harness identity, repository scope, and delegated operator

The user correction is authoritative:
- Codex sends messages to Archon and runs Archon
- Codex must **not** directly patch `AGENTS.md` as if it were `Hermes`
- Codex is a delegated access layer for invoking Archon and relaying artifacts, not `Hermes` itself

## Architecture/spec guidance

### 1. Canonical harness role model

Clarify the roles as follows:

| Component | Role |
|---|---|
| Codex | Delegated access/operator layer for invoking Archon, relaying artifacts, and passing messages; not `Hermes` |
| Archon / Athena | Architecture/spec/planning harness |
| Hermes | User-facing meta-harness/router that routes work to individual Project Koios repositories and their appropriate local harness flows |
| opencode / Vulcan | Implementation/test/validation harness |
| Goose / Koios | Knowledge/provenance/vault harness |

### 2. Routing model to document

Document the desired operating model explicitly:
- `Hermes` receives or brokers user work at the Project Koios level
- `Hermes` routes work to the correct individual repository
- each repository may run its **own local meta-harness instance** for repo-scoped execution and handoffs
- `projectkoios-bootstrap` owns the shared bootstrap/config/workflow guidance for those harnesses
- repo-local meta-harness artifacts, local run state, and repository-specific operational rules are scoped to their own repository, not to `projectkoios-bootstrap`

### 3. Boundary clarification for this repo

Document that `projectkoios-bootstrap` owns:
- shared bootstrap instructions
- shared config examples
- shared workflow conventions
- shared handoff/provenance conventions
- guidance for how harnesses interoperate across repositories

Document that `projectkoios-bootstrap` does **not** own:
- product/domain architecture for unrelated repos
- repo-local meta-harness run history/state
- repo-local implementation plans except when copied here as bootstrap examples/templates
- the authoritative working state of downstream repositories

### 4. Codex clarification language

Replace ambiguous phrasing like "Codex may perform Hermes actions" with language that states:
- Codex may invoke Archon workflows and relay artifacts on behalf of an operator
- Codex may carry out delegated operator/run-control steps when the workflow requires access mediation
- Codex must identify itself as delegated access or operator mediation, not as `Hermes`
- Codex must not collapse provenance fields by presenting Archon-produced output as if it were directly authored by `Hermes`

### 5. Provenance/header guidance to add

Retain the required handoff header convention, but plan to extend guidance so handoffs also capture a provenance block or equivalent fields for:
- `Origin` — original harness/system where the task originated
- `From` — immediate sender/producer of the artifact
- `Acting-As` — harness role identity being performed, if different from sender
- `To` — intended consumer
- `Scope` or `Repository` — repository/repo-scope the artifact applies to
- `Delegated-Operator` — access layer or human/operator mediator, when present

Interpretation rule:
- `From` answers who produced/sent this artifact
- `Acting-As` answers which harness role the sender was representing, if any
- `Delegated-Operator` answers who mediated access without becoming that harness
