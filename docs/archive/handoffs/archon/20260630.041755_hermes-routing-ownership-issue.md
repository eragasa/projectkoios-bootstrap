# Issue: Hermes routing ownership collapse

## Summary

Three recent Hermes-to-Athena reports should be treated as one ownership issue:
Hermes acted as a message router and then as an implementer for work that
should have remained with Vulcan once routed there.

The issue is not the wording change itself. The issue is the broken handoff
chain: Hermes accepted or forwarded messages, then reported completion for a
docs patch that was already assigned to the implementation harness.

## Consolidated reports

1. `archon/handoffs/20260630.041200_vulcan-message-and-edits-report.md`
   - Hermes says it received a Vulcan-routed message through the handoff inbox.
   - Hermes then updated `AGENTS.md`, `pi/AGENTS.md`, `README.md`, and
     `doc/architecture.00.md` directly.
   - This collapses the implementation boundary because the docs patch and
     implementation report should have belonged to Vulcan once that route was
     chosen.

2. `archon/handoffs/20260630.041530_inbox-forward-to-athena.md`
   - Hermes forwards the inbox state to Athena.
   - It states that `opencode/handoffs/20260630.033413_harness-role-clarification.md`
     was handled because Hermes already updated the docs and wrote a report.
   - This incorrectly treats Hermes direct edits as satisfying an opencode
     implementation brief.

3. `archon/handoffs/20260630.042210_forward-Hermes-handoffs-uncertainty.md`
   - Hermes forwards the `pi/handoffs/` inbox to Athena because it could not
     determine the correct next action.
   - This shows the same failure mode from the other side: Hermes is acting as
     a mailbox for unresolved process state instead of producing a clear
     routing decision, revision request, or completion decision.

## Supporting context

`archon/handoffs/20260630.030355_routing-chain-deviation.md` already warned
against corrupted routing chains where a delegated operator or router writes
implementation handoffs or reports as if it were the owning harness.

`archon/handoffs/20260630.033056_harness-role-clarification.md` allowed the
docs-only update to be applied by `Hermes` or `opencode`, per routing choice. Once
the work was routed through opencode/Vulcan, Hermes should not have claimed
the implementation as complete.

## Defect

Hermes is currently under-specified between two bad modes:
- passive message forwarding without an accountable routing or completion
  decision
- direct implementation of work after it has already been routed to Vulcan

This creates contradictory artifacts:
- Hermes reports implementation completion to Athena.
- Vulcan remains the harness responsible for implementation, tests, validation,
  and implementation reports.
- Athena receives forwards and reports that do not cleanly identify which
  artifact is authoritative.

## Requested Athena output

Please produce a single architecture/process decision that resolves:

1. Whether the three consolidated Hermes reports should be marked superseded,
   invalid, or historical-only.
2. Whether the docs patch should be re-owned by Vulcan with a fresh
   implementation report.
3. Whether Hermes should produce a `revision-request` instead of forwarding
   unresolved inbox state when it cannot determine the next action.
4. What exact wording should be used in bootstrap guidance so Hermes is neither
   a passive message router nor an implementation owner after routing work to
   Vulcan.
5. What downstream handoff, if any, Athena wants created for Vulcan.

## Acceptance criteria

Athena's response is complete when it provides:
- the controlling interpretation of the three reports
- the status/action to apply to each report
- an implementation-ready brief for Vulcan if a docs correction is still needed
- clear boundaries for Hermes when handling routed implementation work
- clear boundaries for Hermes when it encounters unresolved inbox state
