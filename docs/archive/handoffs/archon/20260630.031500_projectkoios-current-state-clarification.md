# Project Koios current-state clarification after extraction

## Scope

Bound the current architectural meaning of the `projectkoios` mothership after the 2026-06-29 extraction work, and define the next implementation slice needed to restore documentation and routing clarity.

This artifact is an architecture clarification only. It does not authorize code movement or repo modification by itself.

## Architecture spec

### 1. Current role of the mothership

`~/repos/projectkoios` is no longer the implementation home for most Project Koios runtime packages.

Its current role is:
- product-level architecture and ADR home
- transitional shared-code home for `projectkoios.chunking` and `projectkoios.repositories`
- examples/docs/current-state reference point for the namespace package layout

It is **not** currently the canonical home for:
- search/indexing
- API/runtime wiring
- obsidian/vault management
- ingestion
- agent runtime
- workflow engine

Those concerns either already live in sibling repos or should start there directly when implementation begins.

### 4. Do `chunking` and `repositories` remain in the mothership for now?

Yes.

They should remain in `~/repos/projectkoios` for now as transitional shared abstractions.

Reasons:
- `maps/packages.md` still assigns shared abstractions there
- the remaining codebase is centered on those two packages
- no approved replacement shared repo/core repo is documented yet
- moving them now would widen scope beyond clarification/cleanup

Constraint:
- current-state cleanup should clarify that these packages are retained **for now**, not evidence that the mothership still owns broad runtime implementation

### 5. Should mothership current-state cleanup precede `projectkoios-agent`, `projectkoios-workflow`, or `projectkoios-obsidian` work?

Yes.

A bounded mothership current-state cleanup should precede new planned work in all three areas:
- `projectkoios-agent`
- `projectkoios-workflow`
- `projectkoios-obsidian`

Why:
- current docs misstate repo ownership and sequence
- stale names and stale extraction plans will misroute implementation
- downstream MVP selection should start from accurate boundaries
- this cleanup is small, architecture-relevant, and reduces cross-repo confusion cheaply

Boundary on that recommendation:
- this is a docs/boundaries cleanup only
- it should not block urgent bug fixes inside already-extracted repos
- it should block only new planned MVP-selection work that depends on correct ownership/current-state understanding
