# Implementation observations and recommendations for Athena

## Background

During the koios-handoff-operator skill implementation (see
`opencode/handoffs/20260630.144732_koios-handoff-operator-impl-report.md`),
several cross-cutting issues emerged that Athena should resolve before the
next round of work.

## 1. Skill directory naming convention

The skill is at `agents/global/pi/skills/koios-handoff-operator/`.
The hyphenated name prevents the scripts from being a Python package — you
cannot `import` from a directory with hyphens.

**Options:**
- (a) Accept that skill script directories are not Python packages. Scripts
      are invoked via subprocess or path manipulation only.
- (b) Require underscores in skill directory names
      (`koios_handoff_operator/`). That makes them valid Python packages and
      lets tests import cleanly without `sys.path` hacks.
- (c) Keep hyphens for display/convention but add a symlink or alias with
      underscores for importability.

**Impact:** The test file currently uses `sys.path.insert(0, ...)` plus
`# noqa: E402` to import from the scripts directory. If the naming
convention stays hyphenated, every skill test will need this boilerplate.

## 2. Skill placement: runtime namespace vs role namespace

The skill lives at `agents/global/pi/skills/` — under the *runtime name*
(`pi`). But the skill is about *Hermes* operations (session start, routing,
handoff creation). This is the same conflation that the Runtime/Role ADR
addresses.

Until the ADR is resolved, the question is: should new skills go under
the runtime name (`pi/`) or the role name (`hermes/`)? If `hermes/` doesn't
exist yet, do we create it now or wait for the ADR?

**Suggestion:** Answer this in the ADR along with the Runtime/Role
separation, since it is a concrete instance of the same problem.

## 3. Reusable test command runner pattern

`archon_run_watch.py` uses a named module-level function `run_archon()`
that can be swapped for testing. This pattern is likely to repeat across
future skill scripts that talk to CLI tools (archon, git, pi, goose).

Should this pattern be formalised — perhaps as a small utility in
`projectkoios.bootstrap.harness` or as a shared script helper?

## 4. Shared header module as ledger projection foundation

`projectkoios.bootstrap.harness.headers` now exists and is tested.
It is the natural foundation for the handoff-ledger projection
(`archon/handoffs/20260630.141739_handoff-ledger-projection-spec.md`).

**Suggestion:** When Athena produces the ledger projection spec, consider
whether the projection model (message records, transitions, marking) should
live as DataObjects in `harness/data/` alongside `HandoffArtifact`, or in
a new module. The `headers.py` function should remain the single source
of header parsing regardless of the model choice.

## 5. Boundary types for the shared module

`headers.py` currently exports only a regex and a pure function. It defines
no types — callers work with `dict[str, str]`. This is simple but
error-prone (no key validation, no optional-vs-required distinction).

Should `headers.py` graduate to defining a typed header model, or should
that wait until the ledger projection defines its own message schema?
