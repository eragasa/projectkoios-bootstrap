# Harness validation framework — architecture-spec and acceptance criteria

## Scope

### In scope

Define and implement a repo-local validation framework for harness configuration correctness in `projectkoios-bootstrap`.

Initial validation scope:
- `AGENTS.md`
- `pi/AGENTS.md`
- `opencode/AGENTS.md`
- `goose/AGENT.md`
- `doc/meta-harness.md`
- `archon/prompts/harness-routing.md`
- `opencode/rules/*.md`
- `opencode/checklists/*.md`
- `agents/global/**/*.example`
- repo-local referenced files under `architecture/`, `doc/`, `maps/`, `archon/`, `opencode/`, `goose/`, `pi/`, `agents/global/`, `scripts/`, and `src/python/` when linked from an in-scope document

### Out of scope

- validating machine-local runtime state in `~/.pi`, `~/.archon`, `~/.opencode`, or `~/.local/share/goose`
- executing external harness binaries (`pi`, `goose`, `opencode`, `archon`) as proof of behavioral correctness
- judging prompt quality or agent usefulness via LLM evaluation
- rewriting markdown into a new schema or non-markdown source of truth
- auto-fixing content in the first implementation
- validating artifacts in `handoffs/` beyond optional filename/header checks if Vulcan needs them later

## Architecture-spec

### Goal

Provide a deterministic, tool-agnostic validator that answers: "Are the repository’s harness configuration documents internally consistent, referentially valid, and aligned with the declared meta-harness contract?"

### What correctness means

A harness configuration is **correct** when all of the following hold:

1. **Structural correctness**
   - required canonical files exist for the repo’s declared harness set
   - each canonical file contains required sections for its role
   - example config files use the expected filename conventions
   - hand-authored docs needed by the bootstrap CLI still exist at the paths the CLI assumes

2. **Referential correctness**
   - relative file references in in-scope markdown resolve to existing repo-local paths
   - referenced harness docs use the actual file names in this repo (for example `goose/AGENT.md`, not an invented plural form)
   - referenced rule/checklist/map files exist

3. **Contract correctness**
   - shared role/routing claims do not contradict harness-local claims
   - artifact ownership and handoff directions are consistent with the root `AGENTS.md` meta-harness model
   - opencode rule references declared in `opencode/AGENTS.md` correspond to actual files
   - global example configs do not materially drift from the repo-local canonical configs they are meant to mirror

4. **Behavioral-intent correctness**
   - validation checks only inspect behavior that is explicitly encoded in repository text
   - “behavioral” means policy consistency, not live agent execution

### Validation dimensions

The validator should implement three dimensions, in order:

#### 1. Lint / structural checks
- presence/absence of canonical files
- required section headings per file type
- duplicate or missing rule references in markdown lists
- malformed fenced command blocks only where the validator depends on them

#### 2. Referential / link checks
- resolve inline code path references and markdown links that point to repo-local files
- validate paths named in CLI/help text where they represent hard dependencies
- detect broken references caused by naming drift

#### 3. Semantic / contract checks
- compare root routing table and harness-local role statements for contradiction
- verify root artifact model/handoff descriptions remain compatible with harness-local handoff instructions
- verify bootstrap CLI assumptions remain compatible with repo layout (for example, files installed or linked by `src/python/projectkoios/bootstrap/commands/install.py` and `init.py`)
- verify example config coverage for each harness defined in `src/python/projectkoios/bootstrap/models.py`

The first release should not attempt natural-language theorem proving. Semantic checks must be implemented as explicit repo-specific assertions.

### Canonical file manifest

The framework should use an internal manifest, not a blanket `**/AGENTS.md` assumption.

Initial manifest:
- root shared contract: `AGENTS.md`
- pi harness doc: `pi/AGENTS.md`
- opencode harness doc: `opencode/AGENTS.md`
- goose harness doc: `goose/AGENT.md`
- meta-harness contract doc: `doc/meta-harness.md`
- routing contract doc: `archon/prompts/harness-routing.md`

This avoids false failures from the repo’s current mixed `AGENTS.md` / `AGENT.md` naming.

### Required section contract

Minimum required headings for phase 1:
- `AGENTS.md`: `## Harnesses`, `## Meta-harness`, `## Directions for all harnesses`, `## Directions for pi`, `## Directions for archon`, `## Directions for opencode`, `## Routing guide`, `## Artifact handoff`
- `pi/AGENTS.md`: `## Direct capabilities`, `## Delegation`, `## Scope`, `## Reference`
- `opencode/AGENTS.md`: `## Workspace layout`, `## Rules`, `## Checklists`, `## Setup per repo`, `## Common commands`, `## Conventions`
- `goose/AGENT.md`: `## Domain`, `## Maps`, `## Vault rules`, `## Handoff support`
- `doc/meta-harness.md`: `## Skill model`, `## Disagreement handling`, `## Completion gates`, `## Escalation rules`
- `archon/prompts/harness-routing.md`: `## Harness definitions`, `## Rules`, `## Output requirement`

### Tooling approach

Implement this as an extension of the existing Python CLI in `src/python/projectkoios/bootstrap/`.

Recommended command shape:
- `projectkoios bootstrap validate-harnesses`

Recommended module layout:
- `src/python/projectkoios/bootstrap/commands/validate_harnesses.py`
- `src/python/projectkoios/bootstrap/validation/__init__.py`
- `src/python/projectkoios/bootstrap/validation/harnesses.py`
- `tests/test__validate_harnesses.py`

Design expectations:
- pure Python, stdlib-first
- no new non-dev dependency unless clearly justified
- deterministic output suitable for local use and CI
- support human-readable text output first; optional JSON output if cheap

### Failure model

Use severity levels:

- **error**
  - broken correctness condition
  - command exits non-zero
  - examples: missing canonical file, broken required path reference, missing required section, contradiction in declared routing ownership

- **warning**
  - suspicious drift or incomplete coverage that does not yet make the repo contract false
  - command exits zero by default
  - optional future `--strict` may promote warnings to failure
  - examples: example config differs only in non-contract prose, duplicated advisory statements, optional section mismatch

- **info**
  - informational summary only
  - examples: files scanned, references validated, skipped files

Recommended exit codes:
- `0` = no errors
- `1` = one or more validation errors
- `2` = validator runtime failure / misuse

### Non-goals

The framework must not:
- parse or validate hidden meaning not expressed in repo text
- require internet access or installed harness CLIs
- mutate files as part of validation
- replace `AGENTS.md` with YAML/JSON metadata
- infer cross-repo product architecture correctness outside this repo
- become a generic markdown linter for the entire repository

## Acceptance criteria

Vulcan’s implementation is acceptable when all of the following are true:

1. A repo-local CLI command exists under the existing `projectkoios` bootstrap CLI that runs harness validation.
2. The command scans the phase-1 in-scope files listed above from repository root.
3. The validator enforces the canonical manifest and does not incorrectly require `goose/AGENTS.md`.
4. The validator reports missing required headings for each canonical file type.
5. The validator reports broken repo-local file references from in-scope markdown.
6. The validator checks that rule/checklist references declared in `opencode/AGENTS.md` exist on disk.
7. The validator checks that files assumed by bootstrap CLI code (`init.py`, `install.py`, `models.py`) exist where those modules expect them.
8. The validator checks that each harness declared in `src/python/projectkoios/bootstrap/models.py` has corresponding global example config coverage, using repo reality rather than a pluralized-name assumption.
9. The validator produces severity-tagged findings and a non-zero exit status on errors.
10. The implementation includes pytest coverage for at least:
    - success on current-valid fixture(s)
    - missing canonical file
    - broken relative reference
    - missing required heading
    - wrong goose filename assumption regression
    - missing opencode rule reference
11. The implementation passes repo validation gates appropriate to this repo: `pytest`, `ruff check .`, `mypy src/python`.
12. The implementation writes an `implementation-report` in `opencode/handoffs/` and records any spec deviations.

## Approach

Use the existing Python CLI/toolchain because this repo already exposes `projectkoios = projectkoios.bootstrap.cli:main` in `pyproject.toml`, and the bootstrap package already owns repo-local harness operations.

Implementation should be manifest-driven, not regex-only. A small set of explicit dataclasses/functions is preferred over a generic rules engine. The first release should encode this repo’s actual contract and be easy to extend as the harness surface grows.

## Implementation steps

1. **Add validation command entrypoint**
   - Update `src/python/projectkoios/bootstrap/cli.py`
   - Add `src/python/projectkoios/bootstrap/commands/validate_harnesses.py`

2. **Add validation domain module**
   - Add `src/python/projectkoios/bootstrap/validation/harnesses.py`
   - Define manifest, required headings, severity model, finding/result dataclasses, and validation functions

3. **Implement structural checks**
   - Validate canonical file presence
   - Validate required headings
   - Validate harness/example coverage against `src/python/projectkoios/bootstrap/models.py`

4. **Implement referential checks**
   - Parse repo-local path references from in-scope markdown conservatively
   - Validate rule/checklist/map/doc references
   - Validate bootstrap CLI path assumptions from `init.py` and `install.py`

5. **Implement semantic contract checks**
   - Compare root routing guidance with `pi/AGENTS.md`, `opencode/AGENTS.md`, `goose/AGENT.md`, and `archon/prompts/harness-routing.md`
   - Verify root artifact/handoff claims are not contradicted by harness-local instructions

6. **Add tests**
   - Add `tests/test__validate_harnesses.py`
   - Use temp fixture repos or fixture directories to exercise failure cases without mutating real repo files

7. **Document usage**
   - Update repo docs only as needed to expose the new command and its purpose
   - Keep doc changes tightly scoped to usage/reference, not new policy

8. **Run validation gates and report**
   - `pytest`
   - `ruff check .`
   - `mypy src/python`
   - write `opencode/handoffs/<timestamp>_harness-validation-framework-implementation-report.md`
