# Architecture request: Colored Petri net meta-harness model

## User direction

The current Project Koios meta-harness needs more structure.

The user wants to model the project as a DAG-style structure, but in the
language of colored Petri nets. The user's coding style is object-oriented,
using DataObjects and ActionObjects.

## Problem context

Recent handoff flow exposed structural ambiguity:
- Hermes can look like a passive message router.
- Hermes can also accidentally act as implementer after routing work to Vulcan.
- Athena, Vulcan, Hermes, and Koios boundaries are currently expressed as prose
  rather than as a machine-checkable process model.
- Handoff artifacts carry typed state, ownership, provenance, and authority, but
  the allowed transitions between those states are not formalized.

## Conceptual direction

Use a colored Petri net as the formal process model for the meta-harness.

A plain DAG gives ordering, but it does not naturally model:
- ownership
- provenance
- artifact type
- artifact authority
- valid/invalid handoff state
- concurrent active handoffs
- revision and rejection paths

A colored Petri net can model these as colored tokens, places, transitions,
guards, and markings.

## Initial model sketch

### Places

Candidate places:
- `user_request`
- `hermes_inbox`
- `athena_inbox`
- `vulcan_inbox`
- `koios_inbox`
- `architecture_spec_ready`
- `implementation_ready`
- `validation_ready`
- `knowledge_capture_ready`
- `completion_review`
- `blocked_or_revision_needed`

### Colored tokens

Tokens are typed artifacts with metadata.

Candidate token shape:

```text
ArtifactToken {
  kind: user-request | architecture-spec | acceptance-criteria |
        implementation-brief | patch | test-results |
        implementation-report | deviation-report | revision-request |
        knowledge-note | provenance-index | routing-decision |
        completion-decision
  origin: harness
  from: agent
  to: agent
  acting_as?: harness
  repository: path/name
  status: draft | active | complete | superseded | invalid
  authority_level: number
  provenance: [...]
}
```

### Transitions

Candidate transitions:
- `classify_request`
- `route_to_athena`
- `produce_architecture_spec`
- `route_to_vulcan`
- `apply_patch`
- `validate_patch`
- `route_to_koios`
- `capture_knowledge`
- `completion_gate`
- `reject_invalid_handoff`
- `request_revision`

### Guards

Guards should make process violations explicit.

Example:

```text
apply_patch enabled only if:
  token.kind == implementation-brief
  token.to == Vulcan
  actor == Vulcan
```

Example:

```text
forward_handoff enabled only if:
  actor == Hermes
  output includes routing-decision | revision-request | completion-decision
```

Example:

```text
complete_implementation enabled only if:
  patch exists
  implementation-report exists
  actor == Vulcan
```

The Hermes/Vulcan ownership bug should become a guard failure:

```text
Violation:
  action: CompleteImplementation
  actor: Hermes
  reason: Only Vulcan may complete implementation work after routing to Vulcan.
```

## Object-oriented implementation style

The user prefers OOP with DataObjects and ActionObjects.

Map the Petri net model as:

- DataObjects:
  - `ArtifactToken`
  - `Place`
  - `Marking`
  - `Provenance`
  - `Authority`
  - `TransitionResult`
  - `Violation`

- ActionObjects:
  - `RouteToAthena`
  - `RouteToVulcan`
  - `ProduceArchitectureSpec`
  - `ApplyImplementation`
  - `ValidateImplementation`
  - `RequestRevision`
  - `RejectInvalidHandoff`
  - `CompleteWork`

## Requested Athena output

Produce an architecture specification for a colored-Petri-net-inspired
meta-harness model for Project Koios.

The spec should include:
- precise terminology for places, colored tokens, transitions, guards, and
  markings in the Project Koios context
- the initial place/token/transition inventory
- the guard rules that prevent Hermes/Vulcan ownership collapse
- the OOP DataObject/ActionObject design shape
- the first implementation slice for Vulcan
- acceptance criteria for a handoff validator or model evaluator
- migration guidance from prose-only handoff rules to machine-checkable process
  rules

## Non-goals

- Do not require replacing Archon workflows immediately.
- Do not require a full Petri net execution engine in the first slice.
- Do not collapse the meta-harness into a simple DAG.
- Do not make Hermes the implementation owner for model implementation.

## Suggested Archon workflow options

### Option 1: `archon-architect`

Use for an architectural sweep and process-model design in this repo.

Pros:
- Best fit for architecture/process restructuring.
- Scans Python, Markdown, and YAML assets.
- Already has a `projectkoios-bootstrap` override and Codex provider.
- Can produce scoped simplifications and validation-oriented changes.

Cons:
- May try to implement scoped changes after planning unless constrained.

### Option 2: `archon-piv-loop`

Use for guided Plan-Implement-Validate work with human review checkpoints.

Pros:
- Good when the model needs iterative user feedback.
- Keeps planning, implementation, and validation explicit.
- Uses Codex provider.

Cons:
- Interactive and potentially slower.
- Better after Athena has a clearer PRD or architecture brief.

### Option 3: `archon-interactive-prd`

Use to turn the concept into a product/process requirements document before
implementation.

Pros:
- Strong fit if the next step is requirements discovery.
- Good for resolving vocabulary, scope, and first-slice boundaries.

Cons:
- Provider is Claude in the current workflow list.
- Produces a PRD, not necessarily a repo-specific architecture spec.

### Option 4: `archon-idea-to-pr`

Use for end-to-end plan, implementation, validation, PR, and review.

Pros:
- Long, complete flow from idea to PR.
- Includes comprehensive review.

Cons:
- Too implementation-heavy before Athena decides the process model.
- Risky while the harness ownership model itself is the subject of design.

## Recommendation

Recommend `archon-architect` first.

Reason: this is an architecture/process-model problem in
`projectkoios-bootstrap`, not yet a feature implementation. `archon-architect`
is the longest appropriate non-PRD flow for an architectural sweep, and it is
already tailored to this repository. Run it with a constraint that Athena should
produce the architecture/process spec and implementation-ready first slice, but
should not let Hermes directly implement the resulting Vulcan-owned work.
