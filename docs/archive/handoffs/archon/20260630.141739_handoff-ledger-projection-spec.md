# Handoff ledger projection — architecture-spec request

## Context

This artifact converts the interview in
`pi/handoffs/20260630.125259_handoff-ledger-interview.md` into an
Athena-facing architecture specification request.

The interview began as a discussion about JSON output for the current handoff
evaluator, but the user reframed the work as a protocol/provenance problem.
The desired first slice is not "add JSON output to the evaluator"; it is:

```text
Build a read-only handoff ledger projection.
```

The current repo already has a small Petri-net-oriented handoff evaluation
surface:

- `src/python/projectkoios/bootstrap/commands/handoff.py`
- `src/python/projectkoios/bootstrap/harness/handoffs/parser.py`
- `src/python/projectkoios/bootstrap/harness/handoffs/evaluator.py`
- `src/python/projectkoios/bootstrap/harness/handoffs/guards.py`
- `src/python/projectkoios/bootstrap/harness/data/artifact.py`
- `src/python/projectkoios/bootstrap/harness/data/marking.py`
- `src/python/projectkoios/bootstrap/harness/data/violation.py`

Athena should specify the next increment on top of that surface rather than
designing an unrelated subsystem.

## User Direction

The user selected the "inferred transition ledger" path from the interview.

Interpretation:

- Existing markdown handoffs remain the source input.
- Each handoff file becomes one message record.
- Each message record gets at least one inferred transition, usually
  `created`, derived from filename/path/header data.
- The projection computes the current marking from those messages.
- Guard violations are emitted against stable message identifiers.
- Every inferred transition must be labeled as inferred, not audited.
- The JSON shape should become the portable protocol surface for future
  consumers.

## Architecture-Spec To Produce

Athena should produce a bounded `architecture-spec` and `acceptance-criteria`
for a read-only ledger projection with this pipeline:

```text
handoff files
-> message records
-> inferred transition history
-> current marking
-> guard violations
-> deterministic JSON projection
```

The spec should define the vocabulary and JSON contract precisely enough that
Vulcan can implement it without further design invention.

### Required Concepts

Define these concepts:

- `message`: one parsed handoff artifact derived from one markdown file
- `message_id`: deterministic stable identifier for that handoff record
- `source_path`: repository-relative handoff file path
- `place`: current Petri-net place, derived from handoff directory
- `payload`: parsed artifact metadata plus body/title summary where useful
- `transition`: process event associated with a message
- `transition.source`: `inferred` or `audited`
- `transition.kind`: initially at least `created`
- `marking`: current mapping of places to message identifiers
- `guard_violation`: deterministic violation bound to message identifiers
- `projection`: complete read-only JSON view emitted by the command

### First-Slice Constraints

The first implementation slice must:

- be read-only
- mutate no handoff files
- add no pub/sub transport
- add no append-only ledger writer yet
- add no external dependency
- preserve existing markdown handoffs as source input
- remain deterministic across repeated runs over the same files
- keep the core model portable to other languages
- label inferred provenance as inferred, not audited
- avoid making `evaluator` the long-term conceptual name

### Out Of Scope

Do not specify or ask Vulcan to build:

- a message bus
- topic subscriptions
- background daemons
- cross-repo transport
- mutation of handoff headers
- an append-only sidecar event store
- conversion of markdown handoffs into a new canonical format
- long-term product architecture for the `projectkoios` mothership repo

## Recommended Command Shape

Athena should decide the exact command name, but the implementation should
remain under the existing bootstrap CLI. Acceptable shapes include:

```bash
projectkoios handoff ledger --json
projectkoios handoff project --json
projectkoios handoff evaluate --json --dry-run
```

Preference: use vocabulary that makes the command a projection of handoff
state, not a passive evaluator report. If the existing `handoff evaluate`
command is extended for compatibility, the JSON schema should still use ledger
projection vocabulary.

## JSON Contract Requirements

The JSON projection should contain, at minimum:

- `schema_version`
- `generated_at` or an explicit statement that the output is stable except for
  generation metadata
- `repo_root`
- `messages`
- `transitions`
- `marking`
- `guard_violations`
- `summary`

Each message should include:

- deterministic `message_id`
- repo-relative `source_path`
- `place`
- artifact `kind`
- header fields already parsed by `HandoffParser`, including `Origin`, `From`,
  `To`, `Acting-As`, `Delegated-Operator`, `Scope`, and `Repository` when
  present
- current `status` when present in the header

Each inferred transition should include:

- deterministic transition identifier or deterministic tuple fields
- associated `message_id`
- `kind`, initially `created`
- `source: inferred`
- evidence fields explaining which file/header/path data produced the
  inference

Guard violations should include:

- violation code
- reason
- affected `message_id`
- affected `source_path`
- severity if the current guard model supports or later adds it

## Acceptance Criteria

Vulcan's implementation is acceptable when all of the following are true:

1. A read-only ledger projection is available from the existing
   `projectkoios` bootstrap CLI.
2. Running the projection over the current repo mutates no files.
3. Existing markdown handoffs remain the only source input for the first slice.
4. Each parsed handoff produces exactly one message record.
5. Message identifiers are deterministic across repeated runs over unchanged
   files.
6. Each message has at least one `created` transition.
7. Every first-slice transition is explicitly labeled with `source:
   inferred`.
8. Transition evidence distinguishes inferred history from audited history.
9. The projection includes a current marking keyed by place name and containing
   message identifiers.
10. Guard violations reference message identifiers and source paths rather than
    only raw filesystem paths.
11. JSON output is deterministic apart from any intentionally documented
    generation timestamp.
12. The implementation adds no new external runtime dependency.
13. Tests cover message ID stability, inferred-transition labeling, marking
    projection, guard violation projection, and no-mutation behavior.
14. Tests cover role/provenance normalization cases such as `Vulcan
    (opencode)`, `Hermes`, `Athena (archon)`, `Codex`, and
    `Delegated-Operator: Codex`.
15. Existing `handoff evaluate` behavior remains compatible unless Athena
    explicitly authorizes a breaking CLI change.

## Implementation Brief For Vulcan

After Athena finalizes the JSON contract, route to Vulcan with an
implementation brief to:

1. Extend or wrap the existing `HandoffParser` / `HandoffEvaluator` flow into a
   read-only ledger projection model.
2. Add dataclasses or typed structures for messages, transitions, and
   projection output.
3. Keep conversion from `HandoffArtifact` to message/projection records pure
   and deterministic.
4. Emit JSON through the existing CLI.
5. Update guard violation output so JSON consumers can resolve violations back
   to message records.
6. Add focused pytest coverage for the acceptance criteria.
7. Write a Vulcan implementation report in `opencode/handoffs/`.

## Open Questions For Athena

1. Should `message_id` be path-derived, content-derived, or a deterministic
   tuple/hash over repo-relative path plus normalized header fields?
2. Should `generated_at` be included by default, or omitted unless requested so
   JSON output remains byte-stable?
3. Should the first command be a new `handoff ledger` command, or should
   `handoff evaluate --json` become the compatibility surface?
4. Should skipped/unparseable handoff files be represented in the projection
   summary, or left out entirely with only counts?
5. Should `Status` be treated as message payload only, or also as input to an
   inferred transition in the first slice?
