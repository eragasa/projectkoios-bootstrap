## Process issues

- User-facing terminology needed provenance qualification: "JSON database" was accurate only as shorthand for a bounded SQLite operational adapter storing schema-backed ADR JSON records and exporting a JSON checkpoint.
- Manifest/report path exactness had to be aligned after report creation because the manifest is generated by code before the final report timestamp is known.
- The existing plain ADR schema has no date/provenance timestamp field, so the source date had to be preserved in sidecar mapping evidence.
- The source ADR filename encodes lifecycle status, while the approved canonical identity rule excludes status from generated identity; this required explicit mapping evidence.

- Decide whether future generated manifests should accept the implementation-report path as input to avoid timestamp drift.
- Consider an ADR schema/provenance extension if source date must become first-class structured data.
- Decide future canonical ADR identity policy: topic-stable, timestamp-stable, or another scheme.
