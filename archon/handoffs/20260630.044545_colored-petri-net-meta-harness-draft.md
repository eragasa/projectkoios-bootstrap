# Draft architecture spec: Colored Petri net meta-harness model

## Provenance note

This is a delegated-operator draft produced because Archon workflow execution
is currently blocked. It is not an Athena-authored final spec until Athena
reviews, revises, or supersedes it.

Source requests:
- `archon/handoffs/20260630.042202_colored-petri-net-meta-harness.md`
- `archon/handoffs/20260630.041755_hermes-routing-ownership-issue.md`
- `archon/handoffs/20260630.044544_archon-executor-blocked.md`

## Scope

Define a first formal process model for the Project Koios meta-harness using
colored Petri net language and an implementation style based on OOP
DataObjects and ActionObjects.

This model applies first to `projectkoios-bootstrap` handoff validation and
meta-harness routing. It should later be reusable by repo-local harness
instances in other Project Koios repositories.

## Problem

Current handoff behavior is governed mostly by prose. That prose is not enough
to prevent two recurring failures:

1. Hermes can become a passive mailbox that forwards unresolved state instead
   of producing a routing decision, revision request, or completion decision.
2. Hermes can accidentally act as implementer after work has already been
   routed to Vulcan.

A plain DAG can order steps, but it does not naturally model ownership,
artifact color, provenance, authority, invalid transitions, concurrent active
handoffs, or revision loops. A colored Petri net can model these directly.

## Design goal

Use a colored Petri net as the process model:

- places represent inboxes and workflow states
- colored tokens represent typed artifacts with provenance and authority
- transitions represent harness actions
- guards define when a transition is legal
- markings represent the current repo-local process state
- violations are first-class outputs when a transition is not allowed

Use OOP to implement the model:

- DataObjects carry state.
- ActionObjects implement transitions and guards.

## Core terms

### Place

A `Place` is a named process location that can contain artifact tokens.

Examples:
- `user_request`
- `hermes_inbox`
- `athena_inbox`
- `vulcan_inbox`
- `koios_inbox`
- `architecture_spec_ready`
- `implementation_ready`
- `validation_ready`
- `knowledge_capture_ready`
- `completion_review`
- `blocked_or_revision_needed`
- `invalid_or_superseded`

### Colored token

A colored token is a typed artifact plus metadata.

Required token color fields:
- `kind`
- `origin`
- `sender`
- `recipient`
- `acting_as`
- `repository`
- `status`
- `authority_level`
- `provenance`

Candidate artifact kinds:
- `user-request`
- `routing-decision`
- `architecture-spec`
- `acceptance-criteria`
- `implementation-brief`
- `patch`
- `test-results`
- `implementation-report`
- `deviation-report`
- `revision-request`
- `knowledge-note`
- `provenance-index`
- `completion-decision`
- `blockage-report`

### Transition

A transition is an action that consumes tokens from places and produces tokens
into places.

Examples:
- `ClassifyRequest`
- `RouteToAthena`
- `ProduceArchitectureSpec`
- `RouteToVulcan`
- `ApplyImplementation`
- `ValidateImplementation`
- `RouteToKoios`
- `CaptureKnowledge`
- `RunCompletionGate`
- `RequestRevision`
- `RejectInvalidHandoff`
- `SupersedeArtifact`

### Guard

A guard is a predicate that must pass before a transition can fire.

Guards answer:
- Is this actor allowed to perform this transition?
- Are the input token kinds correct?
- Does the artifact authority chain permit this action?
- Is provenance complete enough?
- Has this work already been routed to another harness?

### Marking

A marking is the current set of tokens at each place. For this repo, a marking
can be built by parsing `*/handoffs/*.md` headers and classifying artifacts.

### Violation

A violation is a structured explanation of a failed guard. It should be emitted
instead of silently forwarding or consuming invalid artifacts.

Example:

```text
Violation:
  action: CompleteImplementation
  actor: Hermes
  token: implementation-brief
  reason: Only Vulcan may complete implementation work after routing to Vulcan.
```

## DataObject model

### `ArtifactToken`

Fields:
- `id`
- `path`
- `kind`
- `origin`
- `sender`
- `recipient`
- `acting_as`
- `repository`
- `status`
- `authority_level`
- `created_at`
- `delegated_operator`
- `provenance`

### `Place`

Fields:
- `name`
- `accepted_kinds`
- `owner_harness`
- `description`

### `Marking`

Fields:
- `tokens_by_place`
- `source_root`
- `loaded_at`

Behavior:
- returns tokens at a place
- finds active tokens for a harness
- finds contradictory tokens by scope/topic

### `Provenance`

Fields:
- `origin`
- `sender`
- `acting_as`
- `delegated_operator`
- `repository`
- `source_artifacts`

### `Authority`

Fields:
- `level`
- `basis`

Suggested levels:
1. explicit user instruction
2. current repository state
3. passing tests / executable validation
4. approved architecture specification
5. acceptance criteria
6. implementation report
7. knowledge note
8. agent inference

### `TransitionResult`

Fields:
- `ok`
- `action`
- `consumed`
- `produced`
- `violations`
- `notes`

### `Violation`

Fields:
- `code`
- `action`
- `actor`
- `token`
- `reason`
- `required_owner`
- `suggested_next_action`

## ActionObject model

All ActionObjects expose:

```text
enabled(marking, actor, context) -> TransitionResult
apply(marking, actor, context) -> TransitionResult
```

The first implementation can make `apply` read-only and return proposed output
tokens without writing files.

### `RouteToAthena`

Owner:
- Hermes

Input:
- `user-request`
- unresolved `routing-decision`
- `revision-request` requiring architecture

Output:
- `architecture-question` or `architecture-request` token in `athena_inbox`

Guard:
- request has design ambiguity, policy conflict, ADR impact, or unclear
  acceptance criteria

### `RouteToVulcan`

Owner:
- Hermes or Athena, depending on source artifact

Input:
- `architecture-spec`
- `acceptance-criteria`
- `implementation-brief`

Output:
- `implementation-brief` token in `vulcan_inbox`

Guard:
- implementation scope is bounded
- acceptance criteria exist
- no unresolved design ambiguity remains

### `ApplyImplementation`

Owner:
- Vulcan

Input:
- `implementation-brief` in `vulcan_inbox`

Output:
- `patch`
- `test-results`
- `implementation-report`

Guard:
- actor is Vulcan
- token recipient is Vulcan
- source spec is not superseded or invalid

Failure case:
- if actor is Hermes, emit `wrong-implementation-owner`

### `RunCompletionGate`

Owner:
- Hermes

Input:
- `implementation-report`
- `test-results`
- `acceptance-criteria`

Output:
- `completion-decision`
- or `revision-request`

Guard:
- report maps changes to acceptance criteria
- required validation is present or explicitly waived

### `RequestRevision`

Owner:
- Hermes, Athena, or Vulcan depending on defect

Input:
- any contradictory or invalid token set

Output:
- `revision-request`

Guard:
- controlling authority is identified
- responsible harness is identified

### `RejectInvalidHandoff`

Owner:
- Hermes

Input:
- handoff token with invalid provenance, invalid owner, or impossible transition

Output:
- `revision-request` or `invalid_or_superseded` token

Guard:
- invalidity is derived from provenance, authority, or transition ownership

## Required guard rules

### Guard: Hermes is not a passive mailbox

Hermes may forward a token only if it produces one of:
- `routing-decision`
- `revision-request`
- `completion-decision`
- `blockage-report`

Invalid:
- forwarding inbox state with no decision
- saying "I could not determine what to do" without producing a revision or
  blockage artifact

### Guard: Vulcan owns implementation after routing

Once an `implementation-brief` is placed in `vulcan_inbox`, only Vulcan may
produce:
- `patch`
- `test-results`
- `implementation-report`

Hermes may later consume those artifacts for completion gating, but may not
replace them with Hermes-authored implementation completion.

### Guard: Athena owns architecture/specification

Only Athena may produce final:
- `architecture-spec`
- `acceptance-criteria`
- `implementation-brief` derived from design ambiguity

Delegated-operator drafts must remain `draft` until Athena accepts or
supersedes them.

### Guard: Codex delegation is mediation, not identity

If Codex mediates access, artifacts must preserve `Delegated-Operator: Codex`
or equivalent provenance.

Codex-mediated artifacts must not collapse:
- `From`
- `Acting-As`
- `Origin`
- `Delegated-Operator`

### Guard: invalid provenance blocks authority

A token claiming `Origin: pi` but produced by Codex without delegated-operator
metadata cannot be consumed as authoritative pi output.

The correct output is a `revision-request` or `blockage-report`.

## First implementation slice for Vulcan

Implement a read-only handoff model evaluator.

### Scope

Files likely to add:
- `src/python/projectkoios/bootstrap/harness/data/artifact.py`
- `src/python/projectkoios/bootstrap/harness/data/place.py`
- `src/python/projectkoios/bootstrap/harness/data/marking.py`
- `src/python/projectkoios/bootstrap/harness/data/provenance.py`
- `src/python/projectkoios/bootstrap/harness/data/violation.py`
- `src/python/projectkoios/bootstrap/harness/actions/base.py`
- `src/python/projectkoios/bootstrap/harness/actions/guards.py`
- `src/python/projectkoios/bootstrap/harness/handoffs/parser.py`
- `src/python/projectkoios/bootstrap/harness/handoffs/evaluator.py`

Potential CLI:

```bash
projectkoios bootstrap handoff evaluate
```

### Required behavior

The evaluator should:
- parse headers from known handoff directories
- build `ArtifactToken` instances
- assign tokens to places using `To`, `Status`, and artifact kind
- run guard checks for known failure modes
- print violations without modifying files

### Initial violations to detect

1. `hermes-forwarded-without-decision`
2. `wrong-implementation-owner`
3. `delegated-operator-missing`
4. `codex-as-pi-identity-collapse`
5. `active-token-with-complete-report`
6. `implementation-brief-without-acceptance-criteria`

### Acceptance criteria

The first implementation is complete when:
- existing handoff files can be parsed without requiring chat history
- malformed or incomplete headers produce structured warnings
- known Hermes/Vulcan ownership collapse cases are reported as violations
- no files are modified by the evaluator
- tests cover at least:
  - a valid Athena-to-Vulcan implementation brief
  - an invalid Hermes implementation report after Vulcan routing
  - a Codex-mediated artifact with correct delegated provenance
  - a Codex-mediated artifact missing delegated provenance

## Open questions for Athena

1. Should this model live only in `projectkoios-bootstrap`, or should the
   reusable process engine eventually move to `projectkoios-workflow`?
2. Should the first evaluator treat historical completed handoffs as warnings
   only, reserving hard failures for active/pending artifacts?
3. What canonical artifact kind vocabulary should replace ad hoc handoff
   titles?
4. Should command-design handoffs and implementation handoffs use the same net,
   or separate nets with shared token color definitions?

## Non-goals

- Do not build a full Petri net execution engine in the first slice.
- Do not replace Archon DAG workflows immediately.
- Do not make Hermes the implementation owner for this model.
- Do not mutate historical handoffs automatically.
