# Repo-wide global/local split for harness assets in projectkoios-bootstrap

## Scope

Plan a repository layout change for harness assets so committed shared source, optional repo-local overrides, and installed/runtime state are clearly separated.

Harnesses covered:
- pi
- archon
- opencode
- goose

In scope:
- directory model for committed shared assets
- directory model for ignored repo-local overrides
- distinction between repo state vs machine/runtime state
- migration guidance for skills, prompts, workflows, and handoffs
- downstream implementation assignment

Out of scope:
- performing the migration now
- rewriting bootstrap CLI/install logic in this pass
- renaming historical artifacts unless needed by the future implementation plan
- defining final harness-specific runtime schemas in detail

## Problem / motivation

Current layout is confusing because some paths mix three different concerns:
- harness ownership
- tool-native runtime layout
- committed source-of-truth content

Concrete example:
- `archon/skills/.agents/skills/archon`

That path looks partly like checked-in source, partly like installed runtime structure, and partly like Archon-specific ownership, even though `.agents/skills/...` is really reflecting a tool-native layout concern.

Similar ambiguity exists across the repo today:
- committed example assets already live under `agents/global/<harness>/...`
- some harness assets live under harness-owned top-level directories like `archon/prompts/`, `archon/workflows/`, `goose/prompts/`, `pi/agent/skills/`
- some runtime-like layouts appear inside committed trees

This makes it harder to answer:
- what is canonical shared source?
- what is safe to override locally?
- what is generated/installed runtime state?
- which directory should future harness assets live in?

## Goals

1. Establish one repo-wide mental model for harness assets.
2. Separate committed shared source from ignored local overrides.
3. Keep installed machine/runtime state out of committed source trees.
4. Make ownership obvious by placing committed assets under a single harness-keyed root.
5. Preserve each harness’s native installed/runtime layout as an installation concern, not a source-layout concern.
6. Support future bootstrap automation against a predictable source model.
7. Reduce confusion for skills, prompts, workflows, and handoff artifact placement.

## Non-goals

- No immediate migration of existing files in this artifact.
- No commitment that all harnesses must expose identical asset types.
- No change to user home/runtime conventions beyond clarifying the boundary.
- No requirement that historical handoffs be moved.
- No design here for cross-machine sync of local overrides.

## Proposed direction

Use three distinct layers:

### 1. Committed shared source

Canonical checked-in assets live under:
- `agents/global/<harness>/...`

Examples:
- `agents/global/pi/...`
- `agents/global/archon/...`
- `agents/global/opencode/...`
- `agents/global/goose/...`

This tree is the shared source of truth for repo-distributed harness assets.

### 2. Optional repo-local overrides

Developer-specific, repo-local, normally ignored overrides live under:
- `agents/local/<harness>/...`

Examples:
- `agents/local/pi/...`
- `agents/local/archon/...`
- `agents/local/opencode/...`
- `agents/local/goose/...`

This tree is for local experimentation, machine/user-specific overrides, and uncommitted adjustments that should not pollute shared source.

### 3. Installed machine/runtime state

Installed tool-native state lives outside committed source, typically under home directories or ignored runtime dirs, for example:
- `~/.pi/...`
- `~/.archon/...`
- `~/.opencode/...`
- tool-appropriate Goose runtime state under home/local-share conventions
- other ignored runtime/install directories when needed by bootstrap tooling

This layer may mirror each tool’s native runtime layout, but that layout should not define the canonical committed source layout.

## Proposed directory model

### Canonical source model

```text
agents/
  global/
    pi/
      AGENTS.md.example
      settings.json.example
      models.json.example
      trust.json.example
      auth.json.example
      skills/
      prompts/
      workflows/
    archon/
      config.yaml.example
      skills/
      prompts/
      workflows/
    opencode/
      AGENTS.md.example
      opencode.json.example
      rules/
      checklists/
      prompts/
      workflows/
    goose/
      AGENT.md.example
      .mcp.json.example
      prompts/
      skills/
      workflows/
  local/
    pi/
    archon/
    opencode/
    goose/
```

Notes:
- not every harness must use every subdirectory
- absent folders should mean “not used”, not “forgotten”
- `.example` files remain appropriate for committed templates when the live installed filename is machine-local

### Compatibility principle

Source layout should reflect repo semantics:
- harness
- asset kind
- shared vs local

Runtime/install layout should reflect tool semantics:
- whatever the harness expects on disk at execution time

Bootstrap install/sync steps can translate from source layout to runtime layout.

## Asset mapping guidance

### Skills

Current pain point:
- committed skill source and installed `.agents/skills/...`-style layout are mixed together in places

Direction:
- committed source should live under `agents/global/<harness>/skills/...`
- optional repo-local skill overrides should live under `agents/local/<harness>/skills/...`
- installed runtime skill layout should be materialized into the harness-native runtime location during install/sync

This specifically avoids committed paths like:
- `archon/skills/.agents/skills/...`

### Prompts

Direction:
- move toward `agents/global/<harness>/prompts/...` for committed prompt source
- allow `agents/local/<harness>/prompts/...` for ignored repo-local prompt variants
- keep harness top-level prompt directories only if explicitly retained as compatibility shims during migration

### Workflows

Direction:
- move toward `agents/global/<harness>/workflows/...` for committed workflow definitions
- allow `agents/local/<harness>/workflows/...` for ignored local variants

### Handoffs

Handoffs are artifacts, not installable harness runtime assets.

Direction:
- do **not** force handoffs into `agents/global/...`
- keep harness-owned handoff directories such as:
  - `archon/handoffs/`
  - `opencode/handoffs/`
  - `goose/handoffs/`
  - any future `pi` handoff area if introduced

Reason:
- handoffs are operational artifacts exchanged between harnesses, not reusable runtime config/templates
- keeping them under harness-owned top-level directories preserves current workflow clarity

So the global/local split applies to harness assets such as skills/prompts/workflows/config templates, but not necessarily to operational output artifacts like handoffs.

## Migration notes

### Skills migration notes

- identify committed skill source currently embedded in harness-specific runtime-shaped directories
- relocate canonical source to `agents/global/<harness>/skills/...`
- define whether install/sync preserves tool-native nesting or flattens it during materialization
- update docs to describe source path separately from installed path
- leave historical/runtime-shaped committed paths only as temporary compatibility shims if needed

### Prompts migration notes

- assess current prompt homes such as `archon/prompts/` and `goose/prompts/`
- decide which prompt files are canonical shared assets vs harness-operational docs
- migrate shared prompt source into `agents/global/<harness>/prompts/...`
- reserve `agents/local/<harness>/prompts/...` for ignored local experimentation

### Workflows migration notes

- assess current workflow homes such as `archon/workflows/`
- migrate shared reusable workflow definitions into `agents/global/<harness>/workflows/...`
- document any bootstrap or harness loader changes needed later

### Handoffs migration notes

- keep current timestamp/header convention unchanged
- keep handoff directories harness-owned and top-level for now
- document explicitly that handoffs are excluded from the global/local source split unless a later design introduces a separate artifact model

## Acceptance criteria

This feature request is satisfied when a future implementation lands all of the following:

1. A documented repo-wide convention exists distinguishing:
   - committed shared source
   - ignored repo-local overrides
   - installed/runtime state
2. Canonical committed harness assets have a defined home under `agents/global/<harness>/...`.
3. Repo-local override assets have a defined ignored home under `agents/local/<harness>/...`.
4. Tool-native runtime layouts are treated as install/materialization targets, not as the canonical committed source layout.
5. The confusing mixed-layout pattern exemplified by `archon/skills/.agents/skills/archon` is eliminated or formally deprecated in favor of the new model.
6. Migration guidance exists for at least skills, prompts, workflows, and handoffs.
7. The design covers pi, archon, opencode, and goose explicitly.
8. Bootstrap/docs/install guidance is updated in the implementation phase to reflect the new source-vs-runtime distinction.
9. Historical artifacts are either left in place with compatibility notes or migrated with explicit deprecation handling; no silent layout breakage.

## Open questions

1. Should harness top-level directories like `archon/prompts/` and `archon/workflows/` remain as canonical operational-doc locations, with only installable assets moving under `agents/global/`, or should all shared prompts/workflows move fully under `agents/global/`?
2. Should `pi/agent/skills/` be treated as canonical shared source today, or as an already-runtime-shaped path that should also be normalized into `agents/global/pi/skills/`?
3. For Goose, which assets belong in shared source vs harness-operational docs, especially where prompts act as both reusable assets and operator-facing documentation?
4. Do we want a generated/synced ignored runtime directory inside the repo for testing/bootstrap preview, or only home-directory installs?
5. How should precedence work when both `agents/global/<harness>/...` and `agents/local/<harness>/...` provide the same asset?
6. Should `agents/local/` be fully ignored in git, or should `.gitkeep`/example placeholders be allowed?
7. Which bootstrap commands should own materialization, diffing, validation, and cleanup for the new model?
8. Are there any harness assets besides skills/prompts/workflows/config templates that should also be included now, such as rules, checklists, or model/provider configs?

## Recommended downstream implementation shape

Phase the work:

1. document the convention
2. inventory current assets and classify them
3. define migration map old-path -> new canonical source path
4. update bootstrap/install/sync logic
5. update validators/docs/examples
6. migrate assets with compatibility handling
7. remove deprecated mixed-layout paths after validation
