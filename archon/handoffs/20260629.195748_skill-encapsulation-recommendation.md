# Skill encapsulation recommendation

## Context

During the harness role clarification pass, `.claude/skills/archon/` and
`.claude/skills/manage-run/` were identified as hardcoding harness-specific
directory paths and names. This makes them non-portable — a skill designed
for one harness cannot be trivially attached to another harness without
path edits.

## Problem

Skills in `.claude/skills/` currently reference paths like:
- `.archon/` (user config directory)
- `archon/workflows/` (repo directory)
- `archon/handoffs/`, `pi/handoffs/` (handoff paths)

If skills should be reusable across harnesses (e.g. the same routing skill
used by both Hermes and Athena), these hardcoded paths prevent that.

## Requested output

An architecture-spec exploring encapsulation options:

1. **Config variables** — skills resolve paths through a config or env file
   rather than hardcoding
2. **Relative path resolution** — skills derive harness identity from their
   own location in the filesystem
3. **CLI abstraction** — skills invoke a CLI command that abstracts harness
   boundaries rather than accessing paths directly
4. **Other approaches** — whatever Athena identifies as feasible

The spec should include non-goals, acceptance criteria, and a
recommendation for the next implementation slice.

## Constraints

- Current skills must continue working during migration
- No breaking changes to existing workflow YAML
- The solution should not require directory renames

## Non-goals

- No implementation in this artifact
- No changes to existing skill functionality
